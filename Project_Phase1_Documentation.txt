1. ABSTRACT
================================================================================

The Parking Slot Reservation & Management System is a web-based application designed to eliminate the inefficiencies of manual, first-come-first-served parking allocation in institutions such as campuses, office buildings, and shopping malls. The system allows registered users to view available parking slots in real time, reserve a slot for a specific time window, and receive confirmation of their booking. Administrators can manage parking slots (add, update, remove), monitor occupancy, and oversee all reservations from a central dashboard. By digitizing the reservation process, the system reduces congestion at entry points, prevents disputes over slot ownership, and provides accurate, real-time visibility into parking availability.

================================================================================
2. PROBLEM STATEMENT
================================================================================

Many institutions still rely on manual or unmanaged parking arrangements, where drivers search for available spaces without any prior knowledge of occupancy. This leads to:

Wasted time and fuel as drivers circle the parking area looking for a free slot.
Conflicts between drivers over the same physical slot.
No accountability or record of who parked where and for how long.
Inefficient use of available parking capacity, especially during peak hours.
Difficulty for administrators to track slot usage, misuse, or unauthorized parking.

There is a need for a centralized, reliable system that allows users to reserve a slot in advance and allows administrators to manage and monitor the parking facility efficiently.

4. AS-IS MODEL (Current Manual Process)
================================================================================

A driver arrives at the parking facility with no prior information on slot availability.
The driver drives around searching for an empty slot.
If a slot is found, the driver parks without any formal registration or record.
There is no tracking of which vehicle occupies which slot or for how long.
Disputes (e.g., two drivers claiming the same slot) are resolved informally, often by security personnel.
Administrators have no digital record of occupancy and cannot generate accurate usage reports.

Key weaknesses: time wasted searching, no accountability, no data for planning, frequent disputes.

================================================================================
5. TO-BE MODEL (Proposed System)
================================================================================

A registered user logs into the web system and views a real-time list of available slots.
The user selects a slot and a time window, then submits a reservation request.
The system validates the request (slot availability, valid time range, no conflicts) and confirms the reservation.
On arrival, the user parks in their reserved slot; the slot status updates to "Occupied."
When the reservation period ends, the slot automatically (or manually, via admin) reverts to "Available."
Administrators log in to a management dashboard to add/update/remove slots, view all reservations, and monitor occupancy trends.

Key improvements: no wasted search time, guaranteed slot on arrival, full digital record, reduced disputes, data-driven capacity planning.

7. SOFTWARE QUALITIES APPLIED
================================================================================

Usability – Simple, intuitive forms and clear slot-status indicators (e.g., color-coded availability) so users can complete a reservation with minimal effort.
Reliability – The system consistently prevents conflicting reservations (no double-booking) and accurately reflects real slot status.
Security – Authentication and role-based access control (User vs Admin); input validation to prevent invalid or malicious data entry.
Maintainability – Layered architecture (JSF for presentation, managed beans for logic, Hibernate for persistence) so components can be updated independently.
Performance – Fast retrieval of slot availability using efficient Hibernate queries.
Portability – Built as a standard Java web application, deployable on any servlet container supporting JSF.
Scalability – The data model supports adding more slots, users, or facilities without structural changes.

11. PROJECT IMPLEMENTATION DETAILS
================================================================================

11.1 Entities:
- User: userId, fullName, email, password, role
- ParkingSlot: slotId, slotNumber, location, vehicleType, status
- Reservation: reservationId, slot (FK), user (FK), vehiclePlate, startTime, endTime, status

11.2 CRUD Operations - ParkingSlot:
- Create: Admin can add new parking slots with slot number, location, and vehicle type
- Read: View all slots and their current status
- Update: Admin can modify slot details and status
- Delete: Admin can remove slots from the system

11.3 CRUD Operations - Reservation:
- Create: Users can reserve available slots for specific time windows
- Read: View reservation details and history
- Update: Users can modify their reservations (within valid time constraints)
- Delete: Users can cancel their reservations; slots revert to "Available" status

11.4 Validation Types:
- Client-side validation: JavaScript validation in manage-slots.xhtml and manage-reservations.xhtml
- JSF built-in validation: required="true", <f:validateLength>, <f:convertDateTime>, and <h:message> on XHTML forms
- Server-side/database validation: javax.validation annotations (@NotBlank, @NotNull, @Size, @Email, @Future), entity column constraints, and custom controller checks for time ranges and reservation conflicts

11.5 CSS Implementation:
- Internal CSS: <style> blocks within XHTML pages
- External CSS: Linked .css files (css/user.css, css/admin.css)
- Inline CSS: style="" attributes on individual components

11.6 Robustness / Reliability Fixes (verified during Phase-1 testing):
- Connection pooling: HibernateUtil uses a single, lazily-initialized SessionFactory
  singleton so one JDBC connection pool is shared across all DAO calls (previously a
  new SessionFactory was built on every request, exhausting PostgreSQL connections
  with "too many clients" errors). All DAO Sessions and Transactions are closed in
  finally-safe manner.
- The reservation form now captures the vehicle plate (VehiclePlate), which is NOT
  NULL in the reservations table, preventing constraint violations when reserving.
- Validation messages render correctly: each <h:message> is a sibling component
  (placed AFTER its input, not nested inside it) and every validated input declares an
  explicit id (fullName, email, password, role, slot, vehiclePlate, startTime,
  endTime, slotNumber, location, vehicleType) so field-level messages attach properly.
- Login failure uses a forward (not a redirect) and index renders <h:messages
  globalOnly="true"> so the "Invalid email or password" message is displayed.
  Registration success message is preserved across the redirect via the JSF Flash scope.
- Duplicate email handling: registration now checks for an existing email and shows a
  friendly "already registered" message instead of an unhandled 500 from the
  database unique constraint.
- Navigation links must live inside an <h:form>: the confirmation page's
  "Back to Dashboard" and Logout command links originally rendered
  onclick="...getElementById('null')..." (no form), so clicks did nothing. The page
  is now wrapped in an <h:form> and navigation works correctly.
- Logout support for both roles: a Logout button on the user dashboard and the admin
  page invalidates the HTTP session (FacesContext.getExternalContext().invalidateSession())
  and redirects to the login page (index.xhtml).
- Session/view stability: javax.faces.STATE_SAVING_METHOD=client stores the JSF
  ViewState in the page itself, preventing ViewExpiredException under rapid
  refresh / back-button use.

11.7 Reschedule ("Update" CRUD) Fix:
- Root cause of the "reschedule is in a mess" bug: the reserve panel, the
  reservations table, and the reschedule panel shared ONE <h:form>. Because a
  browser submits every field of a form, clicking Reschedule / Cancel / Save Changes
  also submitted the reserve panel's required fields (vehiclePlate, startTime,
  endTime), which were empty -> Process Validations failed -> the action never ran.
- Fix: the dashboard now uses separate forms with explicit, stable ids:
    - logoutForm      -> Welcome + Logout
    - reserveForm     -> Reserve a Parking Slot panel only
    - reservationTableForm -> "My Reservations" table (Reschedule / Cancel links)
    - rescheduleForm  -> "Reschedule Reservation" panel, its own form, rendered only
                         while an update is in progress
- Each action now validates and submits only its own fields, so Reschedule, Cancel
  and Save Changes all work independently in the browser.
- Reschedule panel: editable Start/End Time (required, yyyy-MM-dd HH:mm, per-field
  message), Status shown read-only (locked to Confirmed; cancellation is done via the
  Cancel button), and a Save Changes button.
- Controller/DAO hardening:
    - ReservationDao.getReservationById(Long) added; prepareUpdateReservation() uses
      it instead of loading every reservation and looping.
    - ReservationDao.isSlotAvailable(slot, start, end, excludeReservationId) added;
      the reschedule conflict check now excludes the reservation being edited so a
      slot never "conflicts with itself".
    - updateReservation() now validates end > start (friendly warning otherwise),
      re-checks slot availability (friendly "not available" warning on overlap),
      preserves the existing status, flashes a success message, and resets the
      editing bean only on success.
- Display polish: reservation table Start/End times and the confirmation page dates
  are formatted with f:convertDateTime pattern="yyyy-MM-dd HH:mm"; the dashboard
  global messages use severity-aware CSS classes (.msgInfo green, .msgWarn orange,
  .msgError/.msgFatal red) added to css/style.css.
- Slot visibility: the reservation confirmation page and the user's reservation
  table now show both the selected slot number AND its location (e.g.,
  "SLOT-B1 located at Basement"), so a user always knows where to park.
- Verified end-to-end with real HTTP POSTs (multi-form ViewState-aware flow):
  login -> click Reschedule (empty reserve panel, no validation spam) -> panel shown
  with prefilled times -> save valid times (302, flash "Reservation updated
  successfully", DB row updated, status stays Confirmed) -> end<=start blocked -> 
  overlapping range blocked -> Cancel deletes the row.
